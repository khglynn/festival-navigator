## Findings

1. **Medium — Connected overlaps incorrectly become a three-card deck**

   [js/v3/events.js:321](<js/v3/events.js:321>) classifies an entire interval-connected cluster as a deck when `c.length >= 3`. It does not establish that three sets are actually simultaneous.

   Failure scenario: one long 8–11 PM set overlaps an 8–9 PM set and a 10–11 PM set. Maximum concurrency is two, but all three collapse into one deck, obscuring their temporal order.

   Verification: a throwaway Node probe passed those three entries to `timetableOf()` and returned:

   ```json
   [{"kind":"deck","items":["Long","Early","Late"]}]
   ```

   The deck decision should be based on peak concurrent count, not connected-component size. Add this bridge case to the model tests.

2. **Medium — Repaint can restore a panel-card zoom onto the inert deck face**

   [js/v3/app.js:408](<js/v3/app.js:408>) restores the deck, then selects the first card matching artist and occurrence. The top artist exists twice: as the inert face created at [js/v3/deck.js:65](<js/v3/deck.js:65>) and as a real panel card at [js/v3/deck.js:145](<js/v3/deck.js:145>).

   Failure scenario: open the Friday Regency deck, zoom the top card, then receive a remote pick/note repaint. The panel reopens, but the zoom anchors to the hidden deck face instead of the panel card.

   Verification: a throwaway JSDOM probe found both `deck-face` and `panel-card`; the selector at line 418 chose `deck-face`. The existing repaint test at [tests/events-wall.test.mjs:301](<tests/events-wall.test.mjs:301>) uses Jyoty, not the duplicated top artist, so it misses this path.

3. **Medium — The implementation and tests contradict MODEL-V3’s locked run copy**

   The locked spec requires:

   - `~ marks a guessed set time — the order is the plan`
   - `Sun · Runs 10 PM – 2 AM`
   - `Guessing they're 3rd of 4`

   The implementation instead:

   - adds a tilde to the close at [js/v3/events.js:248](<js/v3/events.js:248>);
   - uses a curly apostrophe at line 252;
   - adds a terminal period at [js/v3/wall.js:1108](<js/v3/wall.js:1108>).

   The tests explicitly pin these divergent strings at [tests/events-wall.test.mjs:335](<tests/events-wall.test.mjs:335>), so they protect the discrepancy.

   Verification: direct code/spec comparison plus targeted event tests. There appears to be a real product decision underneath this—the data says the 2 AM close is approximate—so the spec and implementation should be reconciled deliberately.

4. **Low — A failed localStorage write can immediately resurrect the previous bucket state**

   [js/v3/filters.js:131](<js/v3/filters.js:131>) prefers any readable stored value over `bucketMemory`. [saveHiddenBuckets():141](<js/v3/filters.js:141>) ignores `saveLS()`’s failure result.

   Failure scenario: storage already contains `["Folsom"]`; the user also hides Afters, but `setItem()` fails because storage is full. The next refresh reads the old value and Afters reappears.

   Verification: a throwaway Node storage stub with readable old data and a throwing `setItem()` returned `["Folsom"]` after attempting to save `["Folsom","Afters"]`. The existing blocked-store test makes reads and writes both throw, so it does not cover partial write failure.
