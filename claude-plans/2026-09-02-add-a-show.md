# Add a show — design proposal (2026-09-02, not built)

**Kevin's ask (2026-09-02):** "Ability to add a show manually / with LLM help
(like you can manually add picks)." A crew should be able to put a show the
festival file does not know about onto the wall: a side party someone found,
a set the official page missed, a bar meetup.

## What it is

A **crew-added show** is a card like any other — pickable by everyone in the
crew, notes on it, in the day's section — that lives in the CREW DOC, not
in the festival file. It shows a small "added by Kat" whisper in its zoom so
nobody mistakes it for the festival's own billing.

## Where it lives

- **Door:** a `+ Add a show` row at the foot of each day's events section
  (and at the foot of the main grid's "Everything else" section), in the
  bucket-chip vocabulary. Never on the timetable itself — the grid is the
  festival's word.
- **Sheet:** the notes sheet's shape (one sheet, Escape closes), fields:
  name (required), night (day tabs as chips), venue (free text, with the
  registry's venue names as suggestions), time (doors or a range, the
  file's own clock strings), a link (ticket page or poster), and a paste box
  for the LLM path (below). Save = one pick for the person who added it.
- **Data:** `festivals[fid].added[id] = { name, night, venue, time, url,
  addedBy: pid, at: iso }` in the crew doc — a keyed object, never an array
  (jsonb_deep_merge replaces arrays). `id` = a slug of night+venue+name.
  Picks key on the show's `name` like every other card, so the name is the
  pick key and cannot be renamed after the first pick (same rule as the
  festival file); an edit that changes the name is a new show.
- **Render:** `events.js` merges `added` into the night's list at read time
  (tagged `added: true`); the wall renders them through the same tile/run
  path, with `stage: "Fri · <venue>"` so factsFor's zoom lines just work.
  The tilde rules apply if a time is a guess.
- **Consent laws hold:** the show is crew-scoped (one circle sees it);
  hiding it is viewer-side.

## LLM help

Paste anything — a ticket URL, an Instagram caption, a screenshot's text —
and Gemini fills the fields (name, night, venue, time, link) for the person
to confirm. The endpoint already exists in spirit: `api/festival-add`
(GEMINI_MODEL, server-side key). A new op `parse-show` takes the pasted
text and returns the fields; the person always confirms on screen before
anything is saved (the same rule festival-add follows). No page fetching in
v1: paste the text, not the URL's contents — fetching arbitrary URLs from
the API is a separate risk decision.

## Sizing

M–L. Sheet + data + render + one API op + tests (doc merge, render, pick
key freeze interaction) + a real-input walk. Worth a short go/no-go from
Kevin on: (1) the door's placement, (2) whether an added show can be
deleted by anyone in the crew or only by whoever added it (my default:
whoever added it, plus a tombstone so the pick history survives), (3) LLM
path in v1 or v2.
